# Editor

Paths in this document are relative to `apps/web`. Overview of the web app: [../web.md](../web.md). UI rules: [../branding.md](../branding.md).

The Image/GIF quick editor: GIFs and still images (PNG, JPEG, WebP); an animated WebP is converted to GIF when it's opened (see [Animated WebP](#animated-webp)). Named for both on purpose, it's not an emote editor or a GIF tool only. "Image/GIF quick editor" is its full name (page title, eyebrow on `/editor`); everywhere else, breadcrumbs included, it's just "editor" (lowercase everywhere, like all the editor's copy, per [voice.md](../voice.md)). In code it's the media editor (`components/editor/media-*`). It's built around Discord emotes (the size meter measures against Discord's 256 KB emote limit, the same on every server), but works for any image. Everything runs locally in the browser.

One editor, two hosts (the public site and the panel) sharing one local library, and the task editor:

- **`/editor`** – public, no account, nothing uploaded. Prerendered start screen, content from the top (not centered): intro, drop zone (`MediaDropzone`: drop anywhere on the page, paste, or pick; GIF/PNG/JPEG/WebP, up to 20 MB; `/editor` imports `ui-sdk.css` too and the zone pins width, border style, font size, colors and the trigger margin, because web.css stays global once any editor route loaded it and used to change the zone between visits) and *recently edited* (`RecentFiles`), then `EditorGuide` (how it works + FAQ, prerendered for search, see [../web.md](../web.md#seo)) and the site `Footer`. The page head carries the `WebApplication` JSON-LD. A chosen file is validated, saved to the local library and opened at `/editor/<key>`, so Back returns to `/editor`. Routes: `editor.index.tsx` (head) + `editor.index.lazy.tsx`; everything under the intro is `EditorStart host="public"`.
- **`/editor/$key`** – client-only. Loads the file and its saved settings from the library and opens the editor; the toolbar has `new file` (back to `/editor`), [add to server](#add-to-server) when the user has a session, and `download` (always enabled once a result exists, file named `<name>.<extension of the result>`; the size note says Discord takes up to 256 KB). Below `sm` the toolbar keeps only `tetra / editor`, add to server and download (the name field shows the name, the `editor` crumb is new file): with all of it the header was wider than a 390px phone already before add to server. An unknown key (other browser, evicted, cleared) shows "this file isn't in this browser" with a way back. Routes: `editor.$key.tsx` + `editor.$key.lazy.tsx`, rendering `LibraryEditor host="public"`.
- **`/panel/editor`**, **`/panel/editor/$key`** – the same two screens inside the panel layout (`host="panel"`), listing and opening the same library files. See [Panel integration](#panel-integration).
- **`/panel/tasks/$taskId`** – a bot task's emote inside the panel layout, with "add to <server>" instead of download. See [Panel integration](#panel-integration).

## Screen

`src/components/editor/media-editor.tsx` holds the edit state; pages pass the toolbar actions and an optional size note as render props. The actions get `MediaEditorState`: `discord`, `name`, `nameValid`, `result`, `pending` (a newer render is running), `fits`. Host options: `section` (the breadcrumb; leave it out when the host has its own header, then `toolbarStart` fills that spot and the first-render overlay covers only the editor, card at the top), `notice` (bars under the toolbar), `discordOnly` (checks on, switch hidden), `initialDiscord`, `outputFormats` (what a still image may become; in Discord emote mode only `EMOTE_FORMATS`, PNG and WebP, of them), `className` (height; full viewport by default).

- **First frame notice**: a WebP that is still animated when it opens (`MediaFile.firstFrameOnly`: the browser couldn't convert it, see [Animated WebP](#animated-webp)) gets a `Notice` bar saying only the first frame opened and a newer browser keeps the animation; `keep the first frame` hides it.
- **Large file notice**: files over 5 MB (`LARGE_FILE_BYTES` in `lib/media/media-file.ts`) open normally, with a `Notice` bar under the toolbar saying the editor is made for smaller files, processing may be slow or fail, and a dedicated tool will do better. `continue anyway` hides it. The hard upload limit is 20 MB (`MAX_FILE_BYTES` in `lib/media/media-file.ts`).
- **First render blocks the editor**: until the first result exists, a `ProcessingOverlay` (`Spinner` + "processing" + file name, plus "<size> is a big file, this can take a minute" over 5 MB) covers the screen and the editor is `inert`. Later renders don't block (see below).
- **Toolbar**: breadcrumb (`tetra / <section> / <name>`, the section links back to `/editor` or `/panel`), `reset`, page actions.
- **Layout** (desktop, `lg`): the page never scrolls. The header and the trim bar are fixed; the sidebar scrolls on its own; the workspace takes the rest. Below `lg` the columns stack and the page scrolls, the workspace is 60vh.
- **Workspace** (`canvas-window.tsx`): a `bg-dots` area that never scrolls, holding one window. Drag its title bar to move it (pointer capture, 1:1 with the grab offset, at least 64 px stay on screen), drag the bottom-right corner to resize it (min 320×240). The chosen position and size are saved in `localStorage` (`tetra:editor-window`, per browser, not per file) when a drag ends. On open, a saved window that isn't fully inside the workspace is forgotten and the default is used instead; during the visit it's only clamped to the workspace, and the choice itself is never overwritten by clamping, so the window grows back when the browser window does. Without a saved choice it follows the workspace, inset by 16 px, or by 56 px on each axis where the workspace is at least 768 px wide / 560 px tall, so the dots around it show it's a window that can be moved and resized (filling the whole workspace hid that). `fit window` or a double-click on the title bar puts it back to that default and forgets the choice. Storage errors (private mode) just mean it starts fitted. Its content gets the body size and fits itself to it.
- **Main area**: one window, no modes. Its title bar says `preview` and holds `fit | actual size` on the right (a `sm` segmented control; the title bar is the drag handle, so `CanvasWindow` ignores pointer downs and double-clicks on buttons and on anything inside `controls`, marked `data-window-control`).
  - *Panes*: original and result side by side, equal (stacked when the window is narrower than 520 px), on `bg-checker`, both images inset 24 px. *Fit* (default) fits both into their pane, so lowering Size shows up as lost detail instead of a smaller picture, with `image-rendering: pixelated` whenever an image is scaled up; *Actual size* shows 1:1 CSS pixels and larger images scroll inside their pane (centered with `m-auto`, so they still scroll from their edge). Images get `max-w-none`: Tailwind's preflight `max-width: 100%` would otherwise squash them. The result's real edges get a gray outline (`outline-neutral-400`, drawn inside the box so it stays visible where a scrolled image meets the pane edge), on the rendered image and on the live preview's box alike, so the frame doesn't jump between drag and render. Each pane has a footer row of the same minimum height (40 px), so the images line up: under the original the shape control and `reset crop`, under the result a one-line hint for the shape. The result's caption shows frames for GIFs and the output format for images. While a newer result renders, the old one stays, dimmed, and the caption says "updating". With *Discord emote* on, an "in chat" row (22 px inline, 48 px jumbo) spans the whole window under both panes; inside the result pane alone it made the panes unequal, so the two images no longer lined up.
  - *Cropping on the original*: in *Fit* the original pane is a controlled ui-sdk `ImageCropper` (`media-cropper.tsx`) whose viewport fills the pane (`bg-checker`, `p-6`), and ui-sdk fits the image inside the padding. The image's real edges are a gray outline on the `<img>` itself, under the selection (`z-10`), so the selection's orange outline and handles always draw over it and the dim outside the selection covers the pane evenly. The padding is there because with `overflow: hidden` and none, a selection covering the whole image lost its outline and handles at the edges. The selection and each handle are focusable (Tab) and move with the arrow keys (Shift for ten times as far); focus rings are `brand-300`, from the keyboard only. In *Actual size* the original shows the crop read-only: an orange outline drawn inside its box (`-outline-offset-1`, same reason) and the rest dimmed. A crop covering the whole image is stored as `null`.
  - *Draft and commit*: `useCropDraft` keeps the crop as shown (the draft) apart from the edit. A drag or a key press updates the draft on every step (`onCropChange`; changes with reason `image-load`, `aspect-ratio-change` or `imperative` only echo the crop passed in and are ignored); `onCropCommit` (pointer up, each key press) writes it to the edit, and only that starts a render. Until a result exists for the geometry on screen (crop after fitting + fitting, compared as a key; the geometry of a result is noted when it arrives, since older runs are discarded), the result pane draws it with CSS instead (`LiveResult`): the original `<img>` positioned inside an `overflow: hidden` box of the predicted result size (`predictDimensions` of the draft), scaled per axis, so *stretch* squeezes it like the render will; dimmed and captioned "updating" like a pending render. `object-view-box` was skipped because Firefox doesn't have it. A failed render shows its error once the draft has caught up with the edit.
  - *Trim* (animated GIFs only): two-thumb slider over a film strip of 16 frames, in **frame indices** (frames can have different delays), labels in seconds. Handles, dimming and times follow a drag live from a local draft; the edit (and so the render) changes only on release (`onValueCommit`, also once per key press), because every render of a long GIF is a full gifsicle run.
- **Inspector**:
  - *output*: a **Discord emote** switch (off by default on `/editor`, on by default on `/panel/editor`, saved with the file's settings; always on and hidden in the task editor). Emote mode leaves JPEG out of the formats (core's upload endpoints reject it); a saved JPEG choice shows and renders as Auto there and comes back when the switch goes off. A new file's name starts as `toDiscordEmoteName` of the file name ("emote" when nothing usable is left), valid in both modes. On: `emote name` with `:name:` and Discord's rules (2–32 letters/numbers/`_`), the `SizeMeter` against 256 KB, the size note and the chat preview. Off: `file name` with the result's extension as suffix (only characters file systems reject are refused) and a plain size summary (`original → result · −64%`). The name is the download's file name either way.
  - *adjust*, the options:

| Option | GIF | Still image |
|---|---|---|
| Format | – (stays GIF) | `Auto \| PNG \| WebP \| JPEG`, with a one-line hint; Auto names the format it picked |
| Size | longest side, never upscales | same |
| Shape (fitting) | `keep shape \| square \| stretch`, under the original, tied to the crop (below) | same |
| Frame rate, Speed | animated only | – |
| Colors | `--colors` | – |
| Compression | `--lossy` | 0 = lossless; disabled for PNG |
| Trim empty edges | `--crop-transparency` | transparent border cut in the worker |

**Fitting**, labelled *shape* in the UI, decides how the crop becomes the result. Its control (`FittingPicker`) sits in the original pane's footer, next to the crop it changes, with `reset crop` (shown only when there is a crop; it animates back to the whole image, or its middle square under *square*). The stored values stay `contain | cover | fill` (saved edits use them); only the labels are plain words. It works like the bot's (`apps/core` `optimizeBuffer`: `transform: "center"` = cover, `"square"` = fill) but is tied to the crop, so the person always sees what stays:

- *keep shape* (`contain`) – the crop as is, its shape kept.
- *square* (`cover`) – a square crop, nothing distorted. Switching to it sets the crop to the middle square of the current crop (`squareInside`), and the cropper locks to a square (`aspectRatio` 1) the person can move and resize. Switching away restores the crop from before (`cropBeforeCover`, kept for the session).
- *stretch* (`fill`) – the (free) crop squeezed into a square whose side is its longer side, capped by Size (`--resize SxS` for GIFs, a `stretch` resize in the image worker). The bot stretches to the height instead; we use the longer side so nothing is squashed below its detail.

**Shape changes animate the selection** instead of remounting the cropper: from where it is on screen to the new crop, on a critically damped spring (response 0.3 s, no overshoot: 90% of the way at 200 ms, settled at about 500 ms), one rAF loop over x, y, width and height (`useCropDraft.animateTo`). A new shape change mid-flight retargets with the current velocity; grabbing the selection or pressing a key stops it where it is. The square lock waits until the selection lands (it passes through other shapes on the way), and ui-sdk's refit on that ratio change is ignored since the crop is square by then. The edit takes the final crop and the fitting at once, when the change starts, so the render runs during the animation; the result pane shows the live CSS preview until it lands. `prefers-reduced-motion: reduce` jumps straight there. No motion library: apps/web has none, and a 4-value spring is a few lines.

Each option has a small icon (the same wide frame and what happens to it). `predictDimensions` gives the live preview its size (may differ slightly from the render with *Trim empty edges*). `effectiveCrop` still squares a non-square crop under *cover* for older saved edits. Verified on a 128×80 GIF with the WASM build: contain 128×80, cover 80×80 (crop `24,0+80x80`), fill 128×128.

Settings start at the original (full size, no compression): the editor isn't only for emotes. Getting under 256 KB is manual, with the `SizeMeter` showing how much is left to cut.

## Opening a link

Both start screens (`EditorStart`, so `/editor` and `/panel/editor`) have a link field under the drop zone, split from it by a hairline "or" divider (mono, `aria-hidden`).

- **Opens on paste** (the input's value is read on the next tick) **or Enter**, no button. A link pasted anywhere on the start screen (target not an input, textarea, select or contenteditable, no files in the clipboard, text an http(s) URL) fills the field and opens too; pasted files still go to the drop zone, which listens on the document as well. Typing clears the error; a new link aborts the one in flight.
- **Validation**: `parseMediaLink`, an `http://` or `https://` URL with a host. Anything else: "that isn't a link…".
- **Emote pages resolve in the browser, no account**: the resolve endpoint (`GET /emotes/resolve`) needs a session, so the field never calls it, on either host, and both behave the same. Same id rules as core's `parse-emote-link.ts`: a 7TV link (`7tv.app`, `7tv.io`, also CDN links) goes through `GET https://7tv.io/v3/emotes/<id>` (`lookupSevenTvEmote`, same file pick as Browse: 4x GIF for animated, PNG for still); an FFZ link through `GET https://api.frankerfacez.com/v1/emote/<id>` (`lookupFfzEmote`; animated as WebP, see Browse); a BTTV link maps to `cdn.betterttv.net/emote/<id>/3x`. Every other URL is fetched as a direct file. A provider link without an emote id (a user page) says so. Twitch and Discord message links aren't mapped; Discord emoji CDN links work as direct links.
- **Checks** before anything is read, from the headers: `Content-Length` over the 20 MB cap (`MAX_FILE_BYTES`, the drop zone's) → too big; `text/html` → "that link opens a page, not an image"; any other declared type that isn't GIF/PNG/JPEG/WebP → unsupported (a missing or `application/octet-stream` type is left to the bytes). After the download, the size again and the magic bytes (GIF, PNG, JPEG, RIFF/WEBP) decide; the file gets `<name>.<ext>` from the emote's name, or the URL's last path segment.
- **Errors** sit inline on the field (`MediaLinkError.kind`): `invalid`, `page`, `not-found` (provider 404 or a 404 file), `unreadable` (the fetch threw: CORS and network failures can't be told apart, "<source> doesn't let the browser read this file. download it, then drop it here"), `type`, `too-big`, `failed`. While it runs, the description shows a Spinner with "reading <host>", then "downloading <name>".
- Then the file goes the dropped-file way: `importToLibrary` (animated WebP → GIF, `loadMediaFile`, `saveToLibrary`), the host's file route. An FFZ animated emote arrives as WebP and is converted.
- Verified in Bun (no CORS there) on 2026-11: 7TV page → `GIGACHAD.gif`, FFZ page and CDN link → `OMEGALUL.png`, BTTV page → the GIF, a 7TV user page, an unknown 7TV id, `example.com` and plain text → their errors. CORS checked with curl and an `Origin` header: `7tv.io` echoes the origin, `cdn.7tv.app`, FFZ's API and CDN send `*`, `cdn.betterttv.net` only allows `https://betterttv.com`, so **BTTV links always end in the unreadable error in a browser**.

## Local library (`src/lib/media/local-library.ts`)

Optional convenience, all in this browser's IndexedDB (database `tetra-editor`, stores `entries`, `files`, `edits`):

- **Key**: the file name made URL-safe (`Cat JAM!!.gif` → `cat-jam`), a 6-character random id when nothing is left (`🙂.png`). Another file with a taken name gets `-2`, `-3`. The same file again (SHA-256 of its bytes) reopens its entry and its settings instead of adding a copy.
- **Stored**: the original file, a 96 px PNG thumbnail (first frame for GIFs, so the list never loads originals) and metadata in `entries`; the editor's settings, name and Discord toggle in `edits`, saved 400 ms after the last change. Nothing is saved until something changes, so an untouched file opens with the host's default mode (off on `/editor`, on on `/panel/editor`); once edited, the file keeps its own mode in both hosts. **Results are never stored**, they're re-rendered from the settings. `restoreEdit` fills in settings added since and keeps the trim inside the file.
- **Limit**: the 10 most recently opened files; older ones are deleted with everything they stored. `remove` in the list deletes one.
- **Shared by both hosts**: `/editor` and `/panel/editor` list the same files; a file opened in one shows up in the other's recent list, with its saved settings.
- **From an emote**: every "open in editor" (emote menu, selection bar, Quick add, 7TV sync review) is a real link to a new tab, `editorLink` in `components/editor/editor-link.tsx`: the host's start screen with `?open=<file url>&name=<name>` (panel: plus `syncGuild&syncEntry`). `EditorStart` reads it on mount and opens it like a pasted link (`fetchMediaLink` with `name`, which skips the provider lookup: the URL is the file), then replaces the history entry with the file route, so Back doesn't fetch again. Errors show under the link field with the URL filled in. Host: `/panel/editor` inside `/panel`, `/editor` elsewhere (`useEditorHost`). Fetching in the clicking tab and then calling `window.open` was rejected: after the awaits the click's activation can expire and the popup gets blocked; a link also keeps middle-click and copy link working. `?open` without `name` is read like a pasted link (provider pages resolve). The task editor (`/panel/tasks/$taskId`) opens in a new tab too (`taskEditorLink`).
- **Reading a file**: `libraryFileQueryOptions(key)` (`["library-file", key]`, `staleTime` infinite, `gcTime: 0`): the editor page and the panel's breadcrumb share one read, and leaving the page drops it, so the next visit reads the settings saved meanwhile instead of a cached copy.
- **Without IndexedDB** (private mode, blocked storage) files live in memory for the visit, so the editor still works, just without history.
- Safari deletes script-writable storage after 7 days without a visit, so "recent" really means recent there. We don't call `navigator.storage.persist()`: Firefox shows a permission prompt for it.
- Checked with `bun test` against `fake-indexeddb` (keys, dedupe, suffixes, settings round-trip, the 10-file limit, remove).

## Processing

`src/lib/media/` is shared: `media-file.ts` loads a file (`loadMediaFile` sniffs the bytes, so a GIF stays a GIF whatever its extension; still images are measured with `createImageBitmap`), `edit.ts` holds the edit model and defaults, and `render.ts` has `renderMedia(source, edit, signal)`, which picks the engine and returns a `MediaRender` (blob, object URL, size, info, extension, format label).

`use-media-render.ts` renders through `createLatestTask` (`src/lib/latest-task.ts`): every edit aborts the run in flight (its worker is terminated) and starts a new one, and each run carries a version, so a result that still arrives after a newer request is discarded (and its object URL revoked) instead of replacing the newer one. The UI is never locked; during a continuous drag results arrive once the input pauses for as long as one run takes. Errors of aborted runs are ignored. `use-film-strip.ts` (GIFs only) extracts the strip once per file with `--explode` (outputs are `frame.gif.NNN`, sorted numerically).

### GIF engine (`src/lib/gif/`)

[gifsicle](https://www.lcdf.org/gifsicle/man.html) compiled to WASM (`gifsicle-wasm-browser`, pinned). Logic was carried over from the old `tetra-next` `useGifsicle` hook and reworked.

- `parse-gif.ts` – reads size, frame count and per-frame delays from the GIF block structure (no decoding). Delays under 2 cs are stored as 10 cs, which is how browsers play them.
- `gifsicle.ts` – `runGifsicle(buffer, commands, signal)`. The package's own `run()` logs every call and can't be cancelled, so we take its worker blob URL (`gifsicle.tool.worker()`, wasm inlined, the package is dynamically imported on first use) and post `{ data, command, folder, isStrict }` ourselves. One fresh worker per run (the emscripten program runs once); aborting terminates it. `isStrict` is off: strict mode rejects on any stderr line, and gifsicle warns on big files ("huge GIF, conserving memory", reproduced with a 25 MB GIF) while still writing a correct result. A real failure (bad command, broken file) writes nothing to `/out`, so the run returns `[]` and `renderMedia` reports "Processing produced no file." The input is named `input.gif`, `/tem` is scratch space, every file in `/out` is returned.
- `gif-commands.ts` – `buildCommands`, one run with two commands (three for GIFs with per-frame palettes, below):
  1. `-U input.gif -d<cs> #<i> … -o /tem/frames.gif` – trim and frame rate: one frame per `1/fps` slot of playback time, each kept frame shows for the summed delay of the frames it replaces (tempo stays the same), divided by speed, at least 2 cs.
  2. `-U [--crop x,y+wxh] [--crop-transparency] /tem/frames.gif --resize-fit SxS [--colors N] [--lossy=2×compression] -O3 -o /out/emote.gif`.

**Per-frame palettes (ghosting).** gif.ski (common on 7TV) writes every frame with its own 256-color table plus transparency for unchanged pixels. gifsicle can't unoptimize that (`warning: GIF too complex to unoptimize`) and `-U` silently does nothing, so each frame stays a patch over the previous one: dropping frames (trim, frame rate) or resizing leaves ghosts of earlier frames, scattered pixels around moving edges. `parseGif` sets `localPalettes` when any frame has a local color table and transparency; then `prepareInput` first remaps to one shared palette (`input.gif --colors 256 --color-method blend-diversity -o /tem/palette.gif`) and both the render and the film strip read that. Checked with the native binary on `cdn.7tv.app/emote/01JYYRQR9X0SEB6QE8XKWQE90K/4x.gif`, frames 100–200: RMSE vs the original 0.41 → 0.02. Of the palette options, blend-diversity was closest (0.018); `--dither` looked smoother but measured worse and was ~15% bigger. GIFs without such frames skip the extra pass, so they lose nothing.

### Image engine (`src/lib/image/`)

[jSquash](https://github.com/jamsinclair/jSquash) (Squoosh's codecs as WASM; `@jsquash/resize`, `png`, `oxipng`, `webp`, `jpeg`, all pinned). The canvas can't do this alone: Safari's `toBlob` silently returns PNG for WebP, and there's no PNG optimisation.

- `render-image.ts` – starts `image-worker.ts` as a module worker, one per run (aborting terminates it, same as gifsicle).
- `image-worker.ts` – takes the allowed formats with each job (`formats`; all three by default, PNG and WebP in the panel); *Auto* and an explicit format outside them fall back to the allowed candidates. Decodes with `createImageBitmap`, crops on an `OffscreenCanvas`, trims transparent edges, resizes with lanczos3 (premultiplied, linear RGB, only when shrinking), then encodes: PNG → oxipng level 2; WebP lossless at compression 0, else quality `100 − 0.9 × compression`; JPEG quality 95 at 0, else the same formula, flattened onto white. *Auto* compares only formats that keep what the slider promises: PNG and lossless WebP at 0; above that lossy WebP, plus JPEG when nothing is transparent. Smallest wins.
- Vite: `worker.format: "es"` (the worker loads codecs lazily) and `optimizeDeps.exclude` for `@jsquash/*` (pre-bundling breaks their `new URL(…wasm, import.meta.url)` lookups in dev). The `.wasm` files are emitted as assets and only fetched when an image is processed.
- Checked in Bun with the same options as the worker (64 px frame): PNG+oxipng 6.1 KB, WebP lossless 4.1 KB, WebP q55 0.8 KB, JPEG q55 0.9 KB. The full worker (OffscreenCanvas) needs a browser.
- Not supported yet: APNG (only the first frame is read), AVIF output (Discord support unconfirmed), PNG color reduction. Animated WebP never reaches this engine unless the browser couldn't convert it (see below).

### Animated WebP

The editor's engines are gifsicle (GIF) and jSquash (stills), so an animated WebP is turned into a GIF before it enters the library, the same normalization core does in `ProcessingEmoteService.store()`. `importToLibrary` (`lib/media/import-media.ts`) does it for every way in: drop zone, paste, a link (`fetchMediaLink`), "open in editor". The library stores the GIF as `<name>.gif`.

- **Detection from the bytes** (`webpFrameCount` in `lib/gif/webp-frames.ts`), never from the extension or type: RIFF/WEBP with the `VP8X` animation flag (0x02) or `ANMF` chunks; the frame count is the number of `ANMF` chunks (only chunk headers are read). One frame counts as still. A plain WebP (`VP8`, `VP8L`, `VP8X` without the flag) takes the still-image path unchanged.
- **Decoding**: WebCodecs `ImageDecoder` (`type: "image/webp"`) in a worker (`webp-to-gif-worker.ts`), one per conversion, terminated on abort. It returns each frame already composited onto the full canvas (blending and disposal applied); each is drawn on an `OffscreenCanvas` and read back as RGBA.
- **Encoding**: [gifenc](https://github.com/mattdesl/gifenc) 1.0.3 (9 KB minified, 4 KB gzip, only in the worker chunk, ~11 KB with our code). `gif-writer.ts`: per frame, a 255-color palette quantized from the opaque pixels (`rgb565`) plus one transparent entry; alpha under 128 is transparent (GIF has 1-bit alpha); every frame is a full frame with disposal "restore to background". Delay: `VideoFrame.duration` (µs) → cs, under 2 cs → 10 cs (as `parseGif` and browsers). Loop: `repetitionCount` Infinity → forever, n → n extra plays (NETSCAPE semantics), 0 → no loop block.
- The result has local palettes + transparency, so `parseGif` flags `localPalettes` and renders go through the shared-palette pass first; full frames don't ghost.
- **Limits**: the 20 MB cap (`MAX_FILE_BYTES`) applies to the WebP and to the GIF: the worker stops once the GIF passes it and the import fails with "as a GIF this animation is over 20 MB…". The >5 MB notice applies to the GIF as usual.
- **Progress**: after 300 ms the start screen shows "converting the animated WebP to GIF, frame N of M" (Spinner, under the drop zone or in the link field's description; also for `?open`).
- **Fallback**: no `ImageDecoder`, no WebP support in it, or any decode error → the WebP is kept and opens as today (first frame), with the first frame notice. Browser support relied on: `ImageDecoder` in Chromium 94+ (Chrome, Edge), Firefox 133+; Safari's support wasn't checked, the fallback covers it.
- Verified in Bun (no `ImageDecoder` there; sharp decoded the frames instead, composited like `ImageDecoder`) on 2026-11-16 with FFZ's `animated/4` WebPs: 725750 (6 frames, 16 KB → 29 KB GIF), 743169 (6, 21 KB → 39 KB), 724094 (202 frames at 40 ms, 310 KB → 854 KB, encoded in 0.5 s): no transparency mismatches, RGB RMSE 3–4 of 255, delays and loop forever kept; the editor's palette + frame-drop commands on 724094 showed no ghosting. Detection: FFZ animated → frame counts 6/6/202; sharp's lossless (`VP8L`), lossy (`VP8X` with alpha) and opaque (`VP8`) WebPs and a one-frame animation → still. `ImageDecoder` itself, the worker and the UI were not run in a browser.

## Verified gifsicle behavior

Checked against the native binary (1.93) and the WASM build (its worker script evaluated in Bun with browser-worker globals stubbed):

- `-d<cs> #<i>` after the input sets that frame's delay; frames not listed are dropped.
- `--crop` must come before the input file; it's applied before `--resize-fit`.
- `--resize-fit WxH` keeps the aspect ratio and never upscales.
- `--crop-transparency` trims the transparent border shared by all frames.
- `--explode` writes `<output>.<frame number>` per selected frame.

## Decisions and rejected approaches

- **Animated WebP becomes GIF on import**, not a third engine: gifsicle then trims, drops frames and optimizes it like any GIF, and core stores animated WebP as GIF too. gifenc over a gifsicle-only path because gifsicle can't read raw frames; `ImageDecoder` over a WASM WebP demuxer because it composites frames for us and costs nothing to ship.
- **Everything local.** No upload anywhere on `/editor`; WASM engines in workers. The panel sends only the finished result (see [Panel integration](#panel-integration)).
- **The browser fetches files itself, no server proxy.** Opening a remote file in the editor (an emote's "open in editor", a pasted link) is a plain `fetch` from the browser (`fetchMediaLink` in `lib/media/media-link.ts`), saved to the local library and opened like a dropped file. A core endpoint that downloads URLs for the editor was considered and rejected: it isn't needed, since the emote CDNs serve files with CORS. A source without CORS (BTTV) fails in the browser with an error saying so; that's accepted rather than adding a proxy.
- **Renders: abort, don't lock.** Every change aborts the run in flight and versions results (`createLatestTask`). Coalescing (finish the running render, then run the newest) was tried first and replaced; locking the UI during processing was rejected. Only the very first render blocks the screen.
- **Trim commits on release**, sliders don't (yet): a trim drag on a long GIF would otherwise start a full gifsicle run per frame step. If sliders feel heavy, the same draft + `onValueCommit` pattern applies to them.
- **One worker per run** (gifsicle and images): simplest way to cancel. Worker start + wasm compile costs tens of ms per run, fine at these sizes.
- **Settings start at the original**, not at 128 px: the editor isn't only for emotes.
- **No auto-fit.** `fit automatically` (a ladder, `reduceStep`, that raised compression and lowered frame rate, colors and size with real renders until the result fit 256 KB) was removed because it didn't work well (the user's call, 2026-11). Fitting is manual, guided by the `SizeMeter`.
- **Fitting is part of the crop**, set under the original image next to the selection; an earlier version had it in the sidebar next to a separate Square/Free crop toggle, which read as two unrelated settings.
- **No crop mode: the crop is edited on the original pane, next to the result.** Earlier the window switched between Preview (original with a read-only crop outline, and the result) and Crop (a full-window cropper without the result), with the mode repeated in a toolbar segment, the window title's hints and a sidebar "frame" section (`edit in crop` / `exit crop`). The same rectangle lived in two views that each did half the job: in Crop the result was out of sight, in Preview the crop couldn't be moved, and the fitting (which changes the result's shape) was hidden inside Crop. Switching to cover also remounted the cropper (`key`), so the selection jumped, and every drag step started a render, so the result lagged and flickered. Now one view does both, a drag shows its geometry instantly through the CSS preview, and only the release renders.
- **CSS jargon out of the labels**: `contain | cover | fill` became `keep shape | square | stretch`; the stored values stayed so saved edits keep working.
- **Fill stretches to the longer side** (the bot uses the height); see Fitting above.
- **Spinner**: braille frames; an ASCII-ramp spinner jumped because glyph widths and weights differ.
- **ui-sdk `web.css` is global once loaded**, so `/editor` imports it too and the drop zone pins its own styles; ui-sdk's hidden form inputs are `position: absolute`, so scroll containers in the editor are `relative` (see [../web.md](../web.md#ui-sdk)).

## Testing

There's no test runner in the repo yet. What was checked, and how to repeat it:

- **Pure logic** (`latest-task.ts`, `local-library.ts` with `fake-indexeddb`, fitting math in `edit.ts`): `bun test` files kept outside the repo. Run them from `apps/web` so the `@/` alias resolves. Worth committing once a test setup exists.
- **gifsicle commands**: the native binary that core already ships (`node_modules/gifsicle/vendor/gifsicle`) for quick checks, and the real WASM build by evaluating `gifsicle.tool.workerLocalUrl` in Bun with stubbed worker globals (`self` with `postMessage` and `location.href`, `importScripts`, and `process`/`require` set to `undefined` so it doesn't take the Node path).
- **jSquash codecs**: callable in Bun after `init*()` with the wasm read from `node_modules` (the emscripten codecs take an `instantiateWasm` override). `OffscreenCanvas`/`createImageBitmap` aren't available, so the full image worker needs a browser.
- **Not covered by anything automated**: the UI itself (window drag/resize, cropper with its draft/commit, live CSS preview and shape animation, overlay, drop zone), Vite's dev handling of the jSquash wasm, Safari. Check those in a browser after changes.

## Open topics

- Below `lg` the editor stacks and the page scrolls; a fixed mobile layout isn't designed yet.
- Sliders render on every step (aborting the previous run); possibly commit on release like Trim.
- Not supported: APNG input (first frame only), AVIF output, PNG color reduction, GIF output for still images. Animated WebP opens as its first frame only where `ImageDecoder` is missing or fails.
- BTTV links can't open in the browser (no CORS on its CDN); the error says to download and drop the file.
- Very large GIFs (10 MB+) take seconds per render; the 20 MB upload cap is a guess at what browsers handle, not measured.

## Panel integration

Two editors live in the panel, both inside `PanelLayout` in full-bleed mode (see [../web.md](../web.md#panel-layout)).

### Quick editor (`/panel/editor`)

The public editor's screens with the panel around them, from the sidebar's "editor" or "open in editor" on an emote. No duplicated screens: the routes render `EditorStart` and `LibraryEditor` with `host="panel"`.

- **Start** (`/panel/editor`, header `panel / editor`): a short intro, then the drop zone, the link field and recent files, the same library as `/editor`. A file opens at `/panel/editor/<key>`.
- **Paste**: Quick add's paste-anywhere is off on `/panel/editor` and `/panel/editor/<key>` (`QuickAddProvider` matches the route), so a pasted link goes to the start screen's link field and a pasted image to the drop zone; on a file it does nothing.
- **File** (`/panel/editor/<key>`, header `panel / editor / <file name>`, the name from the library entry; the key until it's read): `MediaEditor` without `section` (the panel header is the breadcrumb), `new file` on the left of the toolbar, reset, [add to server](#add-to-server) and download on the right, Discord emote mode on by default; the editor's height is the content area's. A key that isn't in this browser (another browser, evicted, an old `/panel/editor/<taskId>` link) shows the same "this file isn't in this browser" state inline, with "open a file" back to `/panel/editor`.

### Add to server

`/editor/$key` and `/panel/editor/$key` (not the task editor, which has its own add) offer "add to server ▾" left of download.

- **Shown** only in Discord emote mode and when `useCanAddToServer` says the user has a session (`GET /me/state`) with at least one manageable server (`GET /guilds`). On the public editor this runs in the background: it never blocks the editor, redirects or asks to log in; no session, an error or no servers simply leave the button out. The session query is shared with the panel (`["session"]`), with a 5-minute `staleTime` here so refocusing doesn't ask again each time. With the button shown it is the primary (glowing) action and download turns secondary.
- **Lazy**: `AddToServerMenu` (`components/editor/add-to-server-menu.tsx`) and, on the public editor, a `Toaster` load with `React.lazy` only once the user can add, so the public page ships only the two small queries for everyone.
- **Menu**: `ServerMenuItems` (`components/panel/server-menu-items.tsx`, the same rows as the emote menu's add to server: icon, name, "N free" for the result's type, full servers listed but disabled). The type is the source's: animated GIF or static.
- **Enabled** only with a finished, current result (no newer render running) that fits 256 KB and a valid emote name; otherwise the trigger is `focusableWhenDisabled` with a `title` saying why. "adding" while a request runs.
- **Upload**: `useUploadEmote` (`lib/emote-mutations.ts`): result → data URL (`toEmoteDataUrl`, `lib/emote-data-url.ts`, shared with the task add) → `POST /guilds/:guildId/emote/upload` `{ emote, name }`, which core sends to Discord as is (no second optimization). `toast.promise` with `+` / `-`, errors through `emoteErrorMessage` (a 401 says the session ended, and the global 401 handler rechecks the session, so on `/editor` the button goes away). Success moves the slot count of the type from `preview` at once (`holdSlotCounts` + `shiftSlotCounts`, then `refreshSlotCounts`). The editor keeps its state either way, so the same result can go to another server.
- Verified against a mock API: GIF and WebP data URLs, counts move right away (a server at 49/50 animated turns "animated full"), a 409 toasts and keeps the editor, the trigger is off over 256 KB, with an invalid name and while rendering, the switch hides it; keyboard: Tab to the trigger, Enter, arrows (wrapping), Enter adds and focus returns to the trigger. On `/editor` without a session there's no button, no redirect and no script error; the browser itself logs the `401` of `GET /me/state` as a failed resource in the console, which a fetch can't suppress.

### 7TV sync review target

`/panel/editor/$key?syncGuild=<guild id>&syncEntry=<review entry id>` (both or neither, `validateSyncSearch` in `editor-host.ts`; the review list's link passes them through `/panel/editor?open`): a file opened from a server's 7TV sync "needs review" list ("open in editor" there, see [stv-sync.md](stv-sync.md)). `LibraryEditor` gets it as `syncTarget` and swaps "add to server ▾" for one primary "add to <server>" (`AddToSyncButton`, `components/editor/add-to-sync-button.tsx`, lazy like the menu, same enabled rules and `title`), plus a `Notice` bar saying where it goes. The result goes to `POST /guilds/:id/sync/review/:entryId/upload` (same body as the emote upload), which links the new emoji to the 7TV emote; success moves the slot count and goes to the sync page, errors toast and keep the editor. The target lives only in the URL: "new file" or opening the file from recent files drops it.

### Task editor (`/panel/tasks/$taskId`)

`/panel/tasks/$taskId` (`routes/panel.tasks.$taskId.tsx` + `.lazy.tsx`), reached from "fix in editor" on a task tile or "open in editor" in the task emote menu (it lived at `/panel/editor/$taskId` until the quick editor took that path); the header shows `panel / tasks / :name:`.

- **Loading**: `taskQueryOptions` and `taskFileQueryOptions` start together (the file only needs the id). The file comes through core's proxy `GET /tasks/:taskId/file` (third-party hosts don't send CORS headers; never fetch `emote.url` from the browser), read with `unwrapBlob`, then `loadMediaFile`. A dead upstream can take ~30 s, so the file query doesn't retry on its own.
- **States** (inline under a header with the emote's preview, name, server and source; never centered): loading the task; downloading the original (Spinner + "a slow host can take up to half a minute"); `TASK_NOT_FOUND` from either request → "this task is gone" (core answers the same 404 for added, discarded and expired tasks, so the copy names all three, the 14-day / 20-task limits from `lib/retention.ts`, and "open in editor" in Discord as the way back) + back to tasks; `DOWNLOAD_DATA_FAILED` → retry + discard; `URL_NOT_ALLOWED`, `FILE_TOO_LARGE`, `UNSUPPORTED_FILE_TYPE` and a file that won't decode → discard only; anything else → retry.
- **Editor**: `MediaEditor` without `section`, `discordOnly` (so PNG + WebP only: `POST /tasks/:id` takes `data:image/gif|png|webp`, GIFs stay GIFs), name prefilled with the emote's name and checked as typed (`emoteNameError` = core's `EMOTE_NAME_REGEX`). No local library: nothing is saved between visits.
- **Toolbar**: "discard task" on the left (`DiscardTaskDialog`: ui-sdk alert dialog placed at the top third, the confirm runs the `DELETE` as its `action` so it stays open with "discarding" and shows an error inline; 404 counts as done; then toast and `/panel/tasks`). Right: reset and "add to <server>", enabled only with a finished, current result (not while a newer render runs) that fits 256 KB and a valid name.
- **Add**: the result blob → data URL → `POST /tasks/:taskId` `{ emote, name }` in `toast.promise`. Success: navigate to `/panel/servers/$guildId` first (the page observes the task, which 404s from then on), then drop the task from the caches and invalidate `["guilds"]` and that server. Errors toast through `emoteErrorMessage`; the editor keeps its state.
- **Destination notices** from the guilds cache: the server has no free slots of the emote's type (Add stays enabled, the cache may be stale), or the user can't manage it anymore (Add disabled).
- Verified against a mock API with a 1 MB 7TV GIF: fitted to 182 KB with the auto-fit of the time (since removed), POST sends `data:image/gif;base64,…`, error toasts keep the editor, success lands on the server view; the window doesn't scroll at 1440×900 and 1024×768, no horizontal scroll at 390 px.
