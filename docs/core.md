# Tetra core

The Discord bot and the REST API for the panel (`apps/core`). Paths in this document are relative to `apps/core`; commands are run from the repo root.

**Stack:** Bun (runtime, `bun run`, `Bun.spawn`), TypeScript (strict), discord.js 14 with sharding, Hono (API, served by `Bun.serve`), Drizzle + PostgreSQL, Redis (ioredis), sharp + gifsicle (images), yt-dlp + gallery-dl + ffmpeg (`/media`), Zod (validation everywhere).

## Architecture

Two kinds of processes:

- **Manager process** (`src/index.ts`): startup only (temp cleanup in production, continuity cleanup, the **Hono API** when `API_ENABLED`, shard spawn and shutdown hooks). It exports nothing. `shardingManager` and `discordOauth` live in `src/lib/sharding-manager` and `src/lib/discord-oauth`; the API imports them from there.
- **Shard processes** (`src/bot.ts`): discord.js client, events, interactions. Exports `internalClient`. Spawned by `ShardingManager` as child processes (mode `process`, `respawn: true`).

⚠️ Never import `@/bot` from API code (manager process): importing it creates a client and **logs in with the bot token**. To talk to Discord from the API use `discordRestApi` (`src/lib/discord-rest-api`) or `shardingManager.broadcastEval`. The same applies to tests and tools: loading interaction modules can pull in `@/bot` (some button handlers import it), so stub `@/bot` in such tests.

### Process lifecycle

- The manager kills its shards on SIGINT/SIGTERM/exit and disables respawn during shutdown.
- In development a shard exits by itself when its manager is gone (IPC `disconnect`, plus a `process.connected` watchdog); see `src/lib/shards/exit-when-manager-is-gone.ts`. In production this is off: manager and shards run in one container and die together.
- Without these, shards outlive the manager as orphans, each logged into Discord with the same token and running old code (duplicate event handling). Check with `pgrep -fl src/bot.ts`.

### Mechanisms worth knowing

- **Continuity**: a "global" button stores its data in the `continuity` table (Postgres) and its `customId` is `name:uuid`. The handler receives Zod-validated `data`. New button = class extending `BaseContinuity` + `Continuity.create(data)` when rendering. Rows older than 24 h are deleted by the manager (at start, then hourly); a button whose row is gone answers "Interaction expired". Buttons need their row for at most ~6 h (longest-lived state is the 6 h search storage).
- **ProcessingEmoteService**: state of the emote being added lives in Redis with a 15-min TTL, re-armed on every write (reads don't extend it). Its files live in one temp dir per processing key (`tetra-keep-<key>`), removed by a sweeper once the Redis key is gone. `store()` normalizes the file (animated WebP → GIF, animation detected from the file). Always go through this service, never through the files directly.
- **TempFileManager**: `create()` = `tetra-tmp-*` dir for a one-off operation, removed after 15 min; `createPersistent(key)` = `tetra-keep-*` dir tied to a Redis key. Only `tetra-` prefixed dirs are ever deleted, because `TEMP_DIR_PATH` may be the system tmp dir.
- **EmoteStorageService**: search results for pagination, in Redis for 6 h.
- **Redis client** (`src/redis`): one ioredis client per process. ioredis emits `error` on every reconnect attempt; the listener logs once per outage (error code only) and once on recovery. Optional caches go through `boundedRedisCall` (`src/redis/bounded-call.ts`): skipped when the client isn't `ready` or a command takes > 250 ms (ioredis would queue it until reconnect).
- **Optimization**: single entry point `optimizeBuffer` (`src/lib/buffer/optimize-buffer.ts`), used by both the bot (via the `emoteOptimize` wrapper) and the API. Animations: resize to 128 px → ladder of gifsicle presets (binary search). Dropping frames preserves the total delay. It runs in-process, so heavy work in the API blocks the manager.
  - **Per-frame palettes (ghosting)**, verified 2026-11 on gifsicle 1.93 and 1.96: GIFs from gif.ski (common on 7TV) give every frame its own 256-colour table plus a transparent index for unchanged pixels. gifsicle can't unoptimize them (`warning: GIF too complex to unoptimize`, hidden by `--no-warnings`) and `-U` silently does nothing, so dropping or cutting frames leaves ghost pixels and smeared patches from earlier frames. Every `-U` call goes through `process(..., { unoptimize: true })`, which feeds gifsicle a copy remapped to one shared palette (`--colors 256 --color-method blend-diversity`, cached per buffer) when `hasLocalPalettePatches` (`gif-local-palettes.ts`, block walk, no decoding) finds a frame with a local table and transparency; other GIFs skip it, because the remap costs colour accuracy. `--resize`/`--resize-fit`/`--scale`/`--crop` without `-U` handle such files fine (resize-fit RMSE 0.0098 vs the original). Measured on a 286-frame gif.ski 7TV emote (`optimizeBuffer`, drop 2): mean RMSE vs the original 0.049 → 0.040 (cover 0.050 → 0.043, fill 0.053 → 0.048), and the visible smears are gone. The same fix exists in the web editor ([web/editor.md](web/editor.md)).
- **Editor tasks**: "Open in editor" in the bot creates an `editor_tasks` row (+ an `emotes` row with the source file URL); the panel edits the source file in the browser and submits a data URL. Deleting/submitting a task also removes its `emotes` row if nothing else references it. The panel loads the source file through `GET /tasks/:taskId/file` (third-party hosts don't send CORS headers). The browser side is the web editor, see [web/editor.md](web/editor.md#panel-integration-later).
- **Removed emotes**: the panel deletes an emote by inserting `emotes` + `removed_emotes` rows (in a transaction) *before* the Discord delete, and removes them again if Discord refuses. The shard's `emojiDelete` event then finds that row and skips; deletions done in Discord itself are recorded by the event with `deletedWithPanel: false`. Restore re-uploads the image from the Discord CDN.
- **User-facing errors**: throw `EmbeddedError` (`src/constants/errors.ts`), catch it in the handler and pass to `feedback.handleError(error)`. Unknown errors get a tracking ID and are logged.
- **Generic replies** (`FeedbackManager`, `TetraEmbed`): Components v2, compact. One neutral container (accent `#fbfaf9`, the brand's foreground white: the colour is in the reply type's emoji, not the bar), no footer, and no title ever on its own line (height is the point: every extra line and every extra component adds space). The body is one Text Display: the emoji starts the first line, `<emoji> <description>` (the title is dropped), `<emoji> <title>` as plain text when there is only a title, fields as `-# name: value` lines, blank and whitespace-only lines removed; images and buttons follow. Texts carry their key information in the description, so a title adds nothing; embeds from other code that still have a title get it inline (`**Title** · first line`, `inlineTitle`).
- **Texts** (bot replies, buttons, menus, modals, command descriptions, `/media`) follow [voice.md](voice.md): lowercase start, `tetra` lowercase, no trailing period or `!`, no emoji in text, first person in errors (`i couldn't find any emotes`), errors say what to do or give a code, loading without `...` (`working on it`, `downloading from TikTok`), permissions as `you need…`, concrete numbers (sizes through `formatBytes` in `src/utils/format-bytes.ts`: binary units like Discord's limits, `256 KB`, `10 MB`, `8.4 MB`; `FileLimitExceededError(limit, { size | what })` and `ResourceTooLargeError(limit, size?)` carry them).
- **Error codes** (`src/utils/error-code.ts`): every "something broke on my side" text ends with `try again, and if it keeps happening, report it with code \`A7F2K\``. Codes are 5 characters from an alphabet without 0/O/1/I/L (31^5 ≈ 28.6 M values), so they can repeat: the console line is `[ A7F2K ] 2026-11-16T08:00:43.348Z <error>`, and code + time identify one error. Generated for unknown errors (`FeedbackManager.unhandledError`, `/media`) and for `InternalError` (thrown where something broke on our side, logs when created, e.g. "i lost track of this server"); hand-written codes (`EEBU`, `INTERACTION_OBJECT_MISSING`) stay. The "send error report" forward reads the code back from the reply text (`findErrorCode`) and puts it in the log channel embed (`<command> · code A7F2K`). Shared ones live in `Messages`. Exception: `UrlNotAllowedError` reasons stay as they are, because the API passes them to the panel verbatim (`URL_NOT_ALLOWED`).
  ```
  ┃ <tetra_success> Added `pepeHands` emote :pepeHands: in `Server`
  ┃ [emote image]
  ```
  - `TetraEmbed.*` still returns embeds (neutral colour, the compact body in `description`); `FeedbackManager.sendMessage` converts every embed it gets into a container (`src/utils/discord/components-v2.ts`: one Text Display per embed with the title inline (`inlineTitle`), description, fields and footer, thumbnail as a Section, image as a MediaGallery, embed colour as accent; consecutive untitled embeds of one colour share a container, with neighbouring Text Displays merged, to save height and stay under the 40-component limit). So emote-flow components that build embeds (review, list, optimization, previews) go through unchanged. Action rows stay top-level after the containers. `allowedMentions` is always `{ parse: [] }` (embeds never pinged, Text Displays do).
  - **v2 rules it keeps**: a message with `IsComponentsV2` can never lose it and rejects `content`/`embeds`, so every message the manager creates is v2 from its first reply. Edits keep v1 semantics: without `embeds`/`content` the current body stays, without `components` the current rows stay (the manager remembers what it sent, otherwise reads `interaction.message` or `fetchReply()`). `removeComponents()` drops the rows and, as before, the attachments, plus gallery items that point at them; an edit with new `files` drops gallery items pointing at other uploads (a reference to a missing attachment is rejected). Discord rejects a v2 message without components, an empty Text Display and an empty container, so an edit that would empty the message keeps the previous body and its attachments (with nothing to keep, a component interaction is only acknowledged), and containers left empty by dropped galleries are removed.
  - **Legacy messages**: buttons on messages sent before the switch (continuity rows live 24 h) are v1; a component interaction on a message without the flag keeps sending embeds, so they never get a mixed edit.
  - `feedbackPayload(type, content, { rows, ephemeral })` (`src/utils/discord/feedback-payload.ts`, also `FeedbackManager.payload`) builds a fresh reply in the same style for code outside a manager message: the "menu expired" and "error reports aren't set up" ephemeral notices, `/media` states, the preview command. `FeedbackManager.errorRows()` / `panelRows()` are the "send error report" and "open panel" rows.
  - Direct edits outside the manager that had to know about v2: `cancel-interaction` (its "cancelled" text becomes a Text Display on v2 messages, `content` on v1) and `submit-error-log` (keeps the error container and swaps only the row; forwards the text of v2 error replies, collected from their Text Displays, as the embed description in the log channel).
  - Emojis: one application emoji per type (`tetra_success`, `tetra_error`, `tetra_warning`, `tetra_attention`, `tetra_info`, `tetra_panel`, `tetra_media`, `tetra_premium`, `tetra_working`; list in `src/utils/discord/feedback-emojis.ts`). Each shard fetches `client.application.emojis` once on ready and resolves them by name, since dev and prod are separate apps with different ids. Until they are uploaded, the old coloured squares (`⏳` for working) are used. Upload with `bun --filter @tetra/core emojis:sync` (`src/deploy/sync-emojis.ts`: reads `assets/emotes/feedback/`, `GET`/`POST /applications/{id}/emojis` with the current env's token, skips names that exist; `--force` deletes and re-uploads those whose CDN image differs from the file). Run it once per app (dev `.env`, then prod).
  - Preview: `/internal-feedback` (`src/interactions/commands/internal/chat-input/feedback.ts`; internal commands only load in development and are registered by `deploy:dev` on `DEV_GUILDS`; it also refuses outside `DEV_GUILDS`) sends `working()` on its reply, every reply type as follow-ups (real texts from `Messages` where they exist, errors with the "send error report" button, panel with its link) and then edits the reply to `success()`.
- **Interaction log**: `interactions` table, id stored as exact `bigint` (snowflakes exceed `Number.MAX_SAFE_INTEGER`), `input` as a plain JSON object.
- **Loggers**: `CoreConsole` / `BotConsole` / `ApiConsole` from `#/loggers`; `.dev.*` logs only in development.

## API

Hono on `Bun.serve` (`src/api/index.ts`), the app is built in `src/api/app.ts`. The web app imports its type (`AppType`) for a typed client, see [web.md](web.md#talking-to-the-api).

- Base path `/api`. Error format everywhere: `{ error: string, reference?: string }` (`reference` = machine code or a hex trace id for 500s), type `ApiErrorBody`. Every error goes through `app.onError` (`src/api/error-handler.ts`); unknown routes answer `404 NOT_FOUND` in the same format.
- **Writing a route**: one file per handler (`<resource>.<action>.ts`) exporting `authFactory.createHandlers(requireAuth, validate(...), handler)` (or `userFactory` + `requireUser`, or `appFactory` for public routes), mounted in the resource router with `.get(path, ...handlers)`. Routers are **chained** (`new Hono().get(...).post(...)`): the chain is what carries the types to the client. Return `c.json(data, status)` with an explicit status. Errors are thrown as `TetraAPIError`, never returned, so they don't appear in the client types.
- **Middleware per route**, not per router: `requireAuth` (session + decrypted Discord `accessToken` + `discordUserId` from the DB) or `requireUser` (also fetches the Discord profile into `user`, one more Discord request, so only where `user` is needed).
- **Validation**: `validate(target, zodSchema)` (`src/api/validate.ts`) answers bad input with `400 INVALID_REQUEST_SCHEMA`; read the result with `c.req.valid(target)`.
- **Error codes** (`reference`, for the panel's toasts). Discord's own errors are mapped in `mapDiscordApiError` (`src/api/error-handler.ts`, codes from `RESTJSONErrorCodes`, re-exported by discord.js) with our message instead of Discord's:
  - `413 EMOTE_TOO_LARGE`: the optimizer couldn't fit 256 KB (`EmoteTooLargeError`, a subclass of `EmbeddedError` thrown by `optimizeBuffer`, so the bot still handles it as before and the API matches the type, not the text), or Discord refused the file size (50138, 50045). Add/restore/upload emote, post task (upload and post task also check the decoded data URL against 256 KB before calling Discord).
  - `409 GUILD_EMOJI_LIMIT_REACHED`: no free slots (30008, 30018 for animated). Add/restore/upload emote, post task.
  - `403 BOT_MISSING_PERMISSIONS`: the bot lost Manage Expressions or access (50013, 50001). Add/restore/remove/upload emote, post task. Not to be confused with `403 MISSING_PERMISSIONS` (the user lacks it).
  - `400 INVALID_EMOTE_NAME`: 50035 with an error under the `name` field. Other 50035s stay `DISCORD_API_ERROR`.
  - `400 INVALID_EMOTE_FILE`: sharp can't read the file (`UnsupportedEmoteFileError` from `normalizeEmoteBuffer`, mapped by type) or Discord rejected the image (50046). Add/restore/upload emote, post task.
  - `413 FILE_TOO_LARGE`: a source download exceeded `MAX_SUPPORTED_SIZE` (10 MB, the bot's limit; `ResourceTooLargeError` from `getBufferFromUrl`). Add/restore emote, task file.
  - `413 PAYLOAD_TOO_LARGE`: request body over 2 MB (`bodyLimit`).
  - `400 DISCORD_API_ERROR`: any other `DiscordAPIError`, with Discord's message.
  - Remove emote answers `GUILD_EMOTE_DELETE_FAILED` for unmapped Discord errors on the delete; restore answers `DOWNLOAD_DATA_FAILED` when the removed image is gone from the CDN.
- **Ready-made emote files** (`POST /guilds/:guildId/emote/upload`, `requireAuth`; `POST /tasks/:taskId`, `requireUser`): body `{ emote, name }`, `emote` a base64 `data:image/(gif|png|webp)` URL that the browser editor already fitted, sent to Discord unchanged (no `optimizeBuffer`). Schema and the local 256 KB check (`readyEmoteBodySchema`, `assertReadyEmoteFits`) live in `guilds.shared.ts`; the size check runs before `getManageableGuild`, so an oversized file costs no Discord request. JSON (not multipart) on purpose: the 2 MB body limit fits a 256 KB file as base64 and Discord takes a data URL anyway. Upload answers `{ message, preview, emote: { id, name } }`; `POST /guilds/:id/emote` and restore answer `{ message, preview }` (`preview` = CDN `.gif` for animated, `.webp` for static).
- **`GET /tasks/:taskId/file`**: the task's source file as a binary body (`c.body(bytes, 200, headers)`), only for the task's owner (`404 TASK_NOT_FOUND` otherwise). Downloaded with `getBufferFromUrl` (`safeFetch`, 10 MB cap, 15 s timeout per attempt, 2 attempts); no host allow-list, because task URLs include plain links the bot accepted. `Content-Type` is sniffed from magic bytes (gif/png/webp/jpeg only, otherwise `415 UNSUPPORTED_FILE_TYPE`), plus `Content-Length`, `Cache-Control: private, max-age=3600`, `X-Content-Type-Options: nosniff`. Errors: `400 URL_NOT_ALLOWED`, `413 FILE_TOO_LARGE`, `502 DOWNLOAD_DATA_FAILED` (upstream 4xx/5xx, network, timeout). Typed client: `$get` then `res.blob()`; only the 200 is in the types.
- **Emote lookup** (`routes/emotes/`, logic in `src/emotes/lookup/`), `requireAuth`, returns the panel's emote shape `{ id, name, previewUrl, url, animated, source: discord|7tv|bttv|ffz|twitch|link, width?, height? }`. `url` is always accepted by `assertAllowedEmoteSourceUrl`, so the panel passes it unchanged to `POST /guilds/:id/emote`. `name` is the source's name (may be invalid for Discord) or a guess (`emote`, or the link's file name/slug) for sources without names (BTTV links, Twitch, Discord URLs without `?name=`, plain links). `width`/`height` = size of the `url` file, only where the provider lists it (7TV, FFZ). Lookup errors (`EmoteLookupError`) map to `400 UNSUPPORTED_LINK`, `400 URL_NOT_ALLOWED`, `404 EMOTE_NOT_FOUND`, `415 UNSUPPORTED_FILE_TYPE`, `413 FILE_TOO_LARGE`, `502 UPSTREAM_ERROR`. Successful results are cached in Redis (sha256 of the input in the key).
  - `GET /emotes/resolve?url=` (≤ 2048 chars): 7TV (`/emotes/<id>`, CDN `/emote/<id>/…`, 24-hex and ULID ids), BTTV (site or CDN, 24-hex id), FFZ (largest number in the path), Discord emoji CDN URL or `<a:name:id>` mention text, Twitch CDN (`/emoticons/v1|v2/<id>`), Tenor/Giphy/Imgur pages (the bot's helpers), and any image link on the allow-list (HEAD through `safeFetch`, GET fallback on 405/501; 4xx → `EMOTE_NOT_FOUND`; non-image `Content-Type` → `UNSUPPORTED_FILE_TYPE`, generic/missing types pass; `Content-Length` > 10 MB → `FILE_TOO_LARGE`). Known host without an emote id (e.g. a 7TV user page) → `UNSUPPORTED_LINK`. Cache 10 min. File choice: 7TV `4x.gif` (animated) / `4x.png`, preview `2x.webp`; FFZ the largest size, animated as `.webp`; BTTV `3x.gif`/`3x.png`, preview `2x.webp`; Discord `.gif`/`.png`; Twitch `default/dark/3.0`.
  - No search endpoint: browse search (7TV, FFZ) runs in the web client, straight against the providers; BTTV browse is disabled (see [web.md](web.md)).
- **Twitch channels** (`routes/twitch/`, logic in `src/emotes/lookup/twitch-channel-lookup.ts`), `requireAuth` (they spend the app's Helix quota), for the panel's channel emotes page. Helix through `twitchApi` (`utils/managers/twitch-manager.ts`, app token) with a 10 s timeout; any Helix failure is `502 UPSTREAM_ERROR`. Cached in Redis through `cached` (successes only).
  - `GET /twitch/channels?query=` (1–100 chars): `{ channels: { id, login, displayName, avatarUrl, live, broadcasterType }[] }`, Helix `search/channels` (which has no broadcaster type) plus one batched `users?id=` call, max 10. Sorted partners → affiliates → the rest; within a group an exact login match first, then Helix's order. Cache 5 min (lowercased query).
  - `GET /twitch/channels/:login` (`[a-zA-Z0-9_]{1,25}`, case-insensitive): `{ id, login, displayName, avatarUrl, broadcasterType: "partner" | "affiliate" | null }`, `404 CHANNEL_NOT_FOUND`. Cache 1 h.
  - `GET /twitch/channels/:channelId/emotes` (numeric id): `{ emotes: (CatalogEmote & { source: "twitch", type, tier: 1 | 2 | 3 | null })[] }`, sorted follower → subscriptions (tier 1–3) → bitstier. `url`/`previewUrl` = CDN `default/dark/3.0` / `2.0`, accepted by `POST /guilds/:id/emote` as is. An unknown id gives `[]` (Helix answers that way). Cache 10 min.
  - 7TV, BTTV and FFZ channel emotes are fetched by the browser (CORS allowed, see [External emote APIs](#external-emote-apis)).
- **User guild list cache** (`src/lib/discord-oauth/user-guilds-cache.ts`): OAuth `/users/@me/guilds` is heavily rate-limited, so `getUserGuilds(discordUserId, accessToken)` caches it in Redis (`oauth-user-guilds:<discord id>`, 60 s) for `GET /guilds` and `getManageableGuild`. Only successful responses are cached, only `id`, `name`, `icon`, `owner`, `permissions`; the token is never in the key or value. The id is `discordUserId` set by `requireAuth` from the `users` row (the cookie's `user_discord_id` is unsigned, never use it). Login (callback) and logout delete the key; concurrent misses of one user share one Discord call. Redis that isn't `ready` or takes > 250 ms is skipped (ioredis would otherwise queue the command until reconnect) and Discord is asked directly. Trade-off: a permission change on Discord shows up in the panel within 60 s; Discord still enforces the bot's own permissions on every write.
- **`GET /guilds`** (dashboard list): one OAuth guild-list request (cached, see above) plus one `broadcastEval` (`collectGuildEmojiSlots`, `guilds.shared.ts`) that gets the user's guild ids as `context` and returns, per guild the shard has, emoji counts + `premiumTier` (counts, not emoji objects, so the IPC payload stays small). Guilds with the bot carry `emojis: { static, animated, limit }`; `guildsWithoutBotAvailableToAdd` doesn't.
- **`broadcastEval` functions are serialized** (discord.js sends `(${fn})(client, context)` as a string to each shard): they can't use imports or anything else from module scope; pass data through `context` (JSON). Type-only imports and `as` casts are fine (erased).
- **Guild access**: `getManageableGuild(guildId, c.var)` (needs `accessToken` + `discordUserId`) (`routes/guilds/guilds.shared.ts`) loads the guild through the bot and checks that the user is in it with `ManageGuildExpressions`; use it in every write endpoint.
- **Auth**: Discord OAuth with a random `state` stored in the session cookie. Cookie `tetra-session` (`src/api/middleware/session.ts`): `httpOnly`, `sameSite: lax`, `secure` in production, unsigned on purpose (it only holds a random 256-bit token checked against the DB), optional `COOKIE_DOMAIN`. Its value is base64 JSON, the format of the `cookie-session` package the Express API used, so old cookies stay valid. `sameSite: lax` requires the panel and the API to be on the same site (same registrable domain; any port on localhost). A cookie without `session_token` (e.g. only a pending OAuth state) answers `401 NO_SESSION` and is kept.
- **Login flow** (`routes/auth/`): the panel starts it with a plain browser navigation (not fetch) to `GET /api/auth?redirect=<path>`. `redirect` is optional and kept only if it is a relative panel path: `/panel`, `/panel/…` or `/panel?…`, at most 512 chars of printable ASCII without space or `\`, and unchanged by URL parsing (no dot segments, encoded dots, `//` in the path); anything else falls back to `/panel` silently. `oauth_state` and `oauth_redirect` are stored next to an existing session, so an abandoned login doesn't log the user out. `GET /api/auth/callback` never answers JSON: it consumes both keys (success or failure, an existing session stays) and redirects to `${FRONTEND_URL}<redirect>`; on failure with `error=<CODE>` set in the query (replacing an earlier `error`; a successful login drops a stale one): `ACCESS_DENIED` (cancelled on Discord, which sends `?error=access_denied&state=…` without `code`; checked before the state), `INVALID_OAUTH_STATE` (missing/mismatched state), `RATE_LIMITED` (auth limiter, handled in `app.onError`, always to `/panel`), `AUTH_CALLBACK_ERROR` (other Discord errors, missing code, token exchange or DB failure). Failures are logged with the first line of the message only: Drizzle appends query params (encrypted tokens) on later lines.
- **Sessions**: 30 days sliding. `sessions.last_used_at` is updated at most once per hour per session, which also re-sends the cookie; idle > 30 days → `401 SESSION_EXPIRED`. Expired rows are deleted hourly by the manager.
- **Rate limiting** (in-memory, per IP): ~120 req/min for `/api`, ~10/min for `/api/auth`; `429 RATE_LIMITED` with `Retry-After`. In production the client IP is the **last** `X-Forwarded-For` entry (exactly one proxy hop, the one Coolify adds; earlier entries are client-controlled), otherwise the socket address. With more proxy hops all clients would share one IP. Responses carry `RateLimit-Limit/Remaining/Reset`.
- **CORS**: origins from `CORS_ORIGINS` (comma-separated), default = `FRONTEND_URL` origin, with `credentials: true`. It is per origin, not per path, so every page of the site (`/editor` as well as `/panel`) can call the API with the session cookie (cookie `path: /`). Other origins get no `Access-Control-Allow-Origin`.
- **Hono behaviour the API relies on** (verified): headers set with `c.header` before a throw are kept on the error response built by `onError` (rate-limit headers, `Retry-After`); a thrown error is turned into a response inside the middleware chain, so middleware after `await next()` still runs (the session middleware clears or re-sends the cookie on 401s).
- **Testing without the bot**: import `app` from `src/api/app.ts` and call `app.fetch(new Request("http://localhost/api/..."), { server: { requestIP: () => ({ address: "10.0.0.1", family: "IPv4", port: 1 }) } })` (vary the address to avoid the rate limiter). Run it from `apps/core` (for `.env`) against a throwaway database: `POSTGRES_PORT=55432 REDIS_PORT=56379 docker compose -p tetra-api-test up -d --wait postgres redis`, `db:push` with `POSTGRES_URL` overridden, and `down -v` afterwards. A user row with `encryptToken("fake")` and a session row give a valid cookie (base64 JSON `{ session_token, user_discord_id }`); endpoints that call Discord then fail on the fake token, which is enough to check auth, validation and errors. Importing `app` doesn't log the bot in.
- **Bun.serve `idleTimeout`** is 120 s: Bun's default (10 s) closes the connection while an emote is optimized in-process.
- **JSON body limit**: 2 MB (editor submits emotes as base64 data URLs; other payloads too). Don't lower it. Over it: `413 PAYLOAD_TOO_LARGE` (checked through `app.fetch`; `Bun.serve`'s own `maxRequestBodySize` default, 128 MB, is far above it).
- **Discord tokens** (`users.access_token`, `refresh_token`) are encrypted with AES-256-GCM (`v1:<iv>:<tag>:<ciphertext>`) using `TOKEN_ENCRYPTION_KEY`. Values without `v1:` are legacy plaintext and get re-encrypted on the next write. Losing or changing the key logs everyone out.
- Guild access checks: the user must be in the guild (OAuth guild list) and have `ManageGuildExpressions` for write endpoints.

## /media

Handlers in `src/lib/media/` (`PlatformHandlerCallback(url, { progress, fileLimit, signal })` → `PlatformResult`, types in `types.ts`); the command matches the URL's hostname exactly or as a subdomain of a platform host, never by substring (the URL goes to tools that fetch it).

| Platform | Tool |
|---|---|
| TikTok video | yt-dlp (`--use-extractors TikTok,vm.tiktok`) |
| TikTok photo post (`/photo/` in the path, or yt-dlp says "Unsupported URL", e.g. short links) | gallery-dl → images + sound downloaded with `getBufferFromUrl` → `render-slideshow.ts` |
| Instagram reel / video post / video carousel | yt-dlp (`Instagram`) |
| Instagram photo post (yt-dlp: "There is no video in this post") | gallery-dl, only with `MEDIA_COOKIES`; files downloaded with `getBufferFromUrl`, max 10 |
| Twitch clip | yt-dlp (`twitch:clips`), title/clipper/broadcaster from its JSON |
| Kick clip (`kick.com/<channel>?clip=<id>`, `kick.com/<channel>/clips/<id>`) | yt-dlp (`kick:clip`; channels, VODs and live answer "unsupported"). No custom emoji, the meta line shows `Kick` |
| YouTube Short or video up to 90 s (`youtube.com/shorts/<id>`, `/watch?v=<id>`, `/embed/`, `/live/`, `youtu.be/<id>`; any `*.youtube.com`) | yt-dlp (`youtube`). The handler rebuilds the link as `https://www.youtube.com/watch?v=<id>` or `/shorts/<id>` (playlist, `t`, `si` params dropped; channels, playlists, search answer "unsupported" before yt-dlp runs) and passes a `check` to `downloadVideoPost` that rejects, from the `-J` metadata and before any download, a missing `duration`, `duration` > 90 s and `live_status` `is_live` / `is_upcoming` / `post_live`. Caption = title, author = `uploader_id` handle without `@`, date from `timestamp` or `upload_date`. No custom emoji (`YouTube · @author · …`). The result's `url` (canonical link) replaces the query-stripped input for "open original" |
| X | vxtwitter API (unchanged) |
| Streamable | Streamable API (unchanged) |

- Both tools run through `Bun.spawn` (`helper/run-command.ts`, no shell, timeouts) with `--ignore-config` / `--config-ignore`; their JSON is validated with Zod. `--use-extractors` keeps yt-dlp off its generic extractor, which would fetch any URL.
- yt-dlp runs twice: `-J` (extract), then `--load-info-json` (download, no second extraction). The loaded JSON is re-sorted on every download attempt, so the download steps down `-S vcodec:h264,res:720|480|360` until the files fit `fileLimit`. `--max-filesize` rejects a format from its metadata or `Content-Length` before downloading; it skips silently (exit 0, no file printed). Videos whose `duration` can't fit even at ~250 kbit/s are rejected without a download.
- `helper/fit-video.ts` re-encodes a download that isn't H.264 or is over its share of `fileLimit`: H.264/AAC, short side ≤ 720 px, ≤ 30 fps, bitrate capped to fit (max 5 Mbit/s). When no format fits at any ladder step, or the post has a single format (the ladder would pick the same one each time; Kick clips are one HLS or mp4 format, 720p–936p60 at ~8 Mbit/s), one last download of up to 4× `fileLimit` is re-encoded to fit. HLS sources have no size before the download, so `--max-filesize` can't stop them early; the duration floor and the job timeout bound them.
- Cookies: `MEDIA_COOKIES` is a base64-encoded Netscape `cookies.txt` (base64 because env UIs mangle its tabs and newlines). `env.ts` decodes and checks it at startup (valid base64, at least one tab-separated 7-field line) and never prints the value. Each run writes the decoded text to its own temp file (mode 600), because both tools write the cookie jar back on exit. To produce it: export cookies from a logged-in **burner** Instagram account (`yt-dlp --cookies-from-browser <browser> --cookies cookies.txt` or a cookies.txt browser extension), then `base64 -i cookies.txt | tr -d '\n'` (macOS) and paste the output into Coolify.
- **Queue** (`src/lib/media/queue/`, pure logic, takes the ioredis clients as arguments): global concurrency 1 across all shards and containers; a job is the whole request (extract, download, re-encode/render, upload). Keys (`media-queue:` prefix): `tickets` zset (member = interaction id, score = `ticketScore(enqueuedAt)`, the one place a premium priority would go), `alive:<ticket>` (waiting ticket heartbeat, TTL 15 s, refreshed every 5 s together with a `ZADD NX` that restores a pruned ticket at its old score), `lock` (running ticket, TTL 30 s, refreshed every 10 s by compare-and-expire), `user:<id>` (one request per user, `SET NX`, TTL 30 s refreshed while the request lives, compare-and-delete). Lua (`scripts.ts`): acquire prunes tickets whose alive key expired (crashed shard), then only the head ticket may `SET NX` the lock; it returns 0 (acquired), the position (1 = next) or -1 (re-enqueue). Waiters wake on `PUBLISH media-queue:released` (one subscriber connection per process via `redisClient.duplicate()`, since a subscribed ioredis client can't run commands) or a 3 s poll. Cleanup (ticket, alive key, owned lock, publish) always runs in `finally`; the user key is released by the command in its own `finally`.
- **Queue timings**: waiting ends 10 min after `interaction.createdTimestamp` ("queue is too long"), the job is aborted after 4 min (`AbortSignal` → `runCommand` SIGKILLs the tools; the upload is skipped if the signal already fired), so a job started at the wait limit ends before the 15-min interaction token does. Losing the lock (heartbeat finds another owner) aborts the job too. Position edits only when the position changed and at most every 5 s.
- **Command flow**: URL and platform check → `claimUser` (before the first reply, so "already have a `/media` download running" is ephemeral) → public "downloading from …" reply → queue (edits to "in queue: #n") → job. **Redis down fails closed**: every queue command needs a `ready` client and answers within 3 s, otherwise the user gets "`/media` is unavailable right now" (ephemeral if it happens at the claim) instead of downloads running without a limit.
- Verified with separate processes against a local Redis (short TTLs): 4 concurrent workers ran strictly one at a time in FIFO order (max concurrency 1, next job started ~10 ms after release via pub/sub); a holder killed with the lock was replaced after the lock TTL; a waiter killed while waiting was pruned after its ticket TTL; the wait limit and the job timeout threw and released everything; a closed Redis gave `MediaQueueUnavailableError`.
- **Output** (`src/components/media.component.ts`): every `/media` reply is Components v2 (`MessageFlags.IsComponentsV2`) from the first reply on, through `MediaReply` in the command. Discord: the flag can never be removed, `content`/`embeds`/`poll`/stickers are rejected with it, and adding it by edit requires clearing `content`/`embeds`, so states are not mixed. Result = one Container with the neutral accent (`#fbfaf9`, no platform colours): MediaGallery (files referenced as `attachment://<name>`, otherwise v2 doesn't show attachments), the caption (plain text from the handler, max 4 lines / 280 chars, `escapeMarkdown`), one `-#` meta line `<emote> @author · <t:…:d> · ❤ 13.6k · 👁 1.6M` (platforms without a custom emoji, Kick, show their name instead: `Kick · @author · …`; missing fields skipped, author cut at 20 chars, ~55 visible chars at most so it stays one line on mobile), and a link button "open original". Status (`<working> downloading from TikTok`, `<working> in queue: #n`, progress as a `-#` line under it), errors (with the "send error report" button; unknown errors get an error code) and the ephemeral "already in progress" / "unavailable" warnings use `feedbackPayload`, the generic reply style. All payloads use `allowedMentions: { parse: [] }`, since mentions in Text Displays ping.
- Numbers use `formatCompactNumber` (`src/utils/format-compact-number.ts`): `999`, `1k`, `13.6k`, `1.6M`, `1.3B`; one decimal, trailing `.0` dropped, rounding that reaches 1000 moves to the next unit (`999_950` → `1M`).
- Tool errors are classified from stderr (`helper/media-errors.ts`): unsupported URL, blocked (YouTube "Sign in to confirm you're not a bot" / "rate-limited", checked before login since its text mentions cookies), login required (incl. "sign in", age-restricted, members-only), region block, not found (incl. "unavailable", YouTube "Private video"), timeout; anything else is logged (last 500 chars of stderr) and answered generically.
- Slideshow (`render-slideshow.ts`, `planSlideshow` holds the timing rules): sharp pads every image to 720x1280 (`contain`, black), ffmpeg concat demuxer with per-slide durations, H.264 yuv420p (limited range) + AAC 128k, `+faststart`, `-tune stillimage`, CRF 23 capped at 1 Mbit/s, 10 fps (1 fps for a single image). Length = min(audio, 90 s) via ffprobe. One image: whole length. n images: audio/n per slide; under 2 s → 2 s each with the audio looped (max 90 s); over 5 s → cycle at 4 s until the audio ends. No audio: 2–3 s per slide, max 90 s, no audio track. Measured worst case (30 noise images, 90 s): 8.9 MB.

### User install

`/media` is the only command with `integration_types` `[GuildInstall, UserInstall]` and `contexts` `[Guild, BotDM, PrivateChannel]`; every other command keeps the defaults (guild install, guild context).

- A user-installed command runs wherever the user is: guilds without the bot, the bot's DM, DMs and group DMs between users (`PrivateChannel`). In a guild without the bot `interaction.guildId` and `member` are set (so `inGuild()` is true) but `interaction.guild` is null and the channel isn't cached; `authorizingIntegrationOwners` holds only the user key. In DMs `guildId` is null.
- Such a command may answer only through the interaction (reply / deferReply / editReply / followUp, within the 15-minute token); no `channel.send`, no channel/guild fetches. `/media` uses `FeedbackManager` (reply, then editReply) and `interaction.attachmentSizeLimit` for its file limit, so it works the same everywhere.
- If the user lacks **Use External Apps** in that guild channel, Discord forces the responses to be ephemeral (only the user sees them).
- Shared path: `interaction-create.ts` lets interactions outside guilds through only for commands whose `metadata.contexts` contains a non-guild context (components always pass: they can only exist on messages such commands produced). The interaction log stores `interaction.guildId` (set also in guilds without the bot), not `guild.id`. Handlers that need the guild (emote flow) keep checking `interaction.guild`.
- Setup (user side): Developer Portal → Installation → enable **User Install** with the `applications.commands` scope. `integration_types` and `contexts` only apply to **global** commands, so re-register with `bun --filter @tetra/core deployCommands` (`src/deploy/deploy-commands-global.ts`, PUTs all global commands). `deploy:dev` registers guild commands on `DEV_GUILDS`, which can't be user-installed.

### Platform facts (verified 2026-11, yt-dlp 2026.10.26, gallery-dl 1.32.20, residential IP, no cookies)

- yt-dlp works for Instagram reels and video posts (one entry per video), TikTok videos (H.264 formats with `filesize` in the metadata), Twitch clips, X, Streamable, YouTube Shorts. It fails on TikTok photo posts ("Unsupported URL"), Instagram photo-only posts ("There is no video in this post") and Reddit (login).
- gallery-dl works for TikTok photo posts without cookies (`-j`: `[2, post]`, `[3, url, {type: image|audio, extension}]`); image and sound URLs download without cookies or special headers. Instagram photo posts redirect to login without cookies. gallery-dl exits 0 on extraction errors: they come as `[-1, {error, message}]` or only on stderr with an empty list.
- Twitch clip formats come without codec info and were all HEVC (360p–1080p, incl. portrait); 720p ≈ 8 Mbit/s (14 s clip = 13.7 MB). Hence the H.264 transcode and the resolution ladder.
- TikTok answers "Your IP address is blocked from accessing this post" for region-blocked posts and also for ids that don't exist.
- TikTok photo-post sound: gallery-dl's audio file is `music.playUrl` and its length equals `music.duration` / `preciseDuration` (checked: 18.3 s, 59.3 s). The item JSON has no start offset or segment fields, so for original sounds it is exactly the post's audio, while for library songs it is the sound's own clip from its start, not necessarily the segment the post uses (not verified on a library-song post).
- The Instagram reel used in tests has no audio track at all; yt-dlp then picks a video-only DASH format, which is correct.
- YouTube extraction needs an external JS runtime for its challenges; yt-dlp uses deno by default (bun still works but is deprecated, yt-dlp issue 16766) plus the `yt-dlp-ejs` solver scripts, which `yt-dlp[default]` pins (`yt-dlp-ejs==0.8.0`), so nothing is fetched remotely and no `--js-runtimes` flag is passed. `-v` shows `JS runtimes: deno-…` and `[jsc:deno]`. Locally deno must be on `PATH` (`brew install deno`).
- YouTube `-J` has `duration`, `title`, `uploader` / `channel`, `uploader_id` (`@handle`), `timestamp`, `upload_date`, `like_count`, `view_count`, `live_status`, and H.264 https DASH formats with `filesize`; with the `-S` ladder a modern Short resolves to `136+140` (720x1280 H.264 video-only + AAC, merged by ffmpeg into mp4, 38 s = 5.1 MB), old videos to the muxed format `18`. `--max-filesize` applies per format: on a too-big video part the audio part still downloads and the attempt prints nothing, so the ladder continues. Unknown ids: "This video is unavailable"; playlist URLs with `--use-extractors youtube`: "No suitable extractor". Datacenter IPs commonly get "Sign in to confirm you're not a bot" (not verified from the server); `MEDIA_COOKIES` applies to YouTube too.

## Security rules

- Every server-side download of a user-supplied URL goes through `src/lib/network/url-guard.ts` (`safeFetch`): private/loopback/link-local/metadata IPs blocked, each redirect hop re-checked. `getBufferFromUrl` reads the body in chunks and stops at `maxBufferSize`, so a missing or false `Content-Length` can't make it buffer more; always pass a limit for user URLs. `POST /guilds/:id/emote` additionally requires https and an allow-listed host (7TV, BTTV, FFZ, Twitch, Discord CDN, Tenor, Giphy, Imgur).
- Records loaded by id must be checked against the guild/user in the URL (no cross-guild/cross-user access).
- Never log tokens, session values or keys.

## Discord platform facts (verified)

- An emoji id belongs to exactly one guild and can be deleted only once; re-adding or restoring creates a new id.
- Deleting an emoji through the REST API (e.g. from the panel) also fires the gateway `emojiDelete` event in the shard (intent `GuildExpressions`).
- Emoji slots per type (static and animated separately): 50 / 100 / 150 / 250 by boost tier. Discord's API docs don't list them (they come from the Boosting FAQ); discord.py's `Guild.emoji_limit` uses the same values and raises the base to 200 when the guild has the undocumented `MORE_EMOJI` feature (old partnered/verified guilds; it appears in the docs' example guild but not in the feature table or `discord-api-types`). `getEmojiSlotLimit` (`src/utils/discord/guild-parse-premium.ts`) does the same, for bot and API.
- Application emojis (`client.application.emojis`) are separate from `guild.emojis`, so guild emoji caches never contain them. Managed emojis (Twitch integration) are not counted as slots in Tetra (bot and API count the same way).
- discord.js `GuildEmoji.deletable` also depends on the bot's own `ManageGuildExpressions` permission; don't use it to count slots.
- Upload limits change over time (free 20 MB since Aug 2026, boost level 2 = 50 MB, level 3 = 100 MB, paid perks up to 250 MB). Don't hardcode them: use `interaction.attachmentSizeLimit` (Discord's `attachment_size_limit`, per attachment).
- Discord only accepts clicks on components that exist on the message, so a button `customId` is always one the bot produced (possibly from an old version).
- Deleted emoji images usually stay on the Discord CDN for a while, but this is not guaranteed.

## External emote APIs

- **7TV**: v3 GraphQL (`7tv.io/v3/gql`) and REST (`/v3/emotes/:id`, `/v3/users/twitch/:id`). Send user text as GraphQL **variables**, never interpolated. v3 is legacy; v4 lives at `api.7tv.app/v4/gql` with a different schema (e.g. `search` requires `sort`). 7TV has short outages; the bot's search retries transient failures only. Verified 2026-11: `emotes(query, page, limit, filter)` caps `limit` and `page` at 100 (higher = GraphQL error); an empty query works, `filter.category` `TOP` = all-time most used (GIGACHAD, catJAM…), `TRENDING_DAY/WEEK/MONTH` = trending, `NEW`/none = newest; no hits = empty `items` (not the old 70429 error). Ids are 26-char ULIDs now; REST `/v3/emotes/<old 24-hex id>` still works and answers with the ULID; unknown id → 404. `host.files` lists `1x`–`4x` in WebP, AVIF and GIF (animated) or PNG (static); 4x is 128 px high.
- **BTTV**: as of 2026-11 the `/3/cached/*` endpoints (incl. `/3/cached/emotes/global`) and the CDN work, but `/3/emotes/{id}`, `/3/emotes/shared/{search,top,trending}` return `403 unauthorized` without auth and v2 is retired (403). So the bot's BTTV search, `/addemote` BTTV links and any BTTV search from the panel fail today; the API resolves BTTV links from the CDN only: `cdn.betterttv.net/emote/<id>/3x` (no extension) serves the original file (gif/png/webp, 404 for unknown ids); `.png`, `.webp` exist for every emote, `.gif` only for animated ones.
- **FFZ**: public REST API, works without auth. `/v1/emotes?q=&page=&per_page=` (`per_page` ≤ 200, `sort=count-desc` = most used; without `q` it lists all emotes), `/v1/emote/<id>` (404 for unknown). CDN (verified 2026-11): static `emote/<id>/<1|2|4>` serves PNG and rejects an extension (`/4.png` → 400); animated `emote/<id>/animated/<n>` serves WebP (`.webp` also works), but `animated/2.gif` and `4.gif` hang without a response (only `1.gif` answers), which affects the bot's FFZ source (it uses `animated/2.gif`).
- **Discord emoji CDN** (verified 2026-11): `cdn.discordapp.com/emojis/<id>.gif` → 200 for animated, 415 for static, 404 for unknown ids; `.webp?animated=true` serves animated WebP.
- **Twitch emote CDN**: `static-cdn.jtvnw.net/emoticons/v2/<id>/default/dark/3.0` serves GIF for animated emotes and PNG otherwise, 404 for unknown ids. Helix has no emote-by-id endpoint, so a link gives no name.
- Twitch emotes come from the Twitch Helix API (`@twurple`, app token from `TWITCH_CLIENT_ID`/`TWITCH_SECRET_KEY`).
- **Helix** (verified 2026-11): `search/channels` returns `thumbnail_url` = the 300x300 profile picture and `is_live`, so search needs no extra call; its ranking is fuzzy (the exact login isn't guaranteed first). `chat/emotes?broadcaster_id=` gives `emote_type` (`follower`, `subscriptions`, `bitstier`), `tier` (`1000`/`2000`/`3000`, null for non-sub emotes), `format` (`static`, plus `animated` when animated), ids `emotesv2_<32 hex>` for new emotes; an unknown broadcaster id answers an empty list. `default/dark/<scale>` on the CDN serves the GIF for animated emotes (checked on an emote with both formats). twurple has no request timeout.
- **Channel endpoints and CORS** (verified 2026-11, simple GET with an `Origin`): 7TV `7tv.io/v3/users/twitch/<id>` and BTTV `api.betterttv.net/3/cached/users/twitch/<id>` echo the origin in `Access-Control-Allow-Origin` (also on 404), FFZ `api.frankerfacez.com/v1/room/id/<id>` sends `*`. BTTV answers a preflight (`OPTIONS`) with 403, so browser requests must stay simple (no custom headers). Unknown or unlinked ids are 404 on all three (7TV `{ error_code: 12000 }`, BTTV `{ message: "user not found" }`, FFZ `{ message: "No such room" }`). A big 7TV channel is ~2.4 MB of JSON (969 emotes, each with tags, owner and `host.files`).

## Bun runtime facts (verified on Bun 1.3.8)

- A forked child is **not** stopped when its parent dies (SIGTERM, SIGKILL or crash); it receives `process.on("disconnect")` and `process.connected` becomes false, but only if something listens on the IPC channel.
- `process.ppid` is not updated after the parent dies.
- `bun --watch` restarts the process in place (same PID) without running exit/signal handlers.
- Native `fetch` is used everywhere (no `node-fetch`).

## Database

- Schema in `src/db/schemas/`, applied with `bun run db:push` (no migration files). `db:push` can propose destructive changes (e.g. truncating a table): read its output, abort anything that isn't additive, and run it on production yourself.

## Docker

- Image: `docker/core.Dockerfile`, built from the **repo root** (it needs the root `bun.lock` and `tsconfig.base.json`). Base `oven/bun` (Debian slim) with `ffmpeg` and `gifsicle` from apt, and deno (`COPY --from=denoland/deno:bin`, official multi-arch single-binary image, latest; yt-dlp's YouTube JS runtime). yt-dlp (`[default,curl-cffi]`) and gallery-dl are pip-installed unpinned into a venv (`/opt/media-tools`, symlinked to `/usr/local/bin`; the build fails if `yt_dlp_ejs` isn't importable); `ADD`ing their PyPI JSON busts the layer cache, so every build gets the latest release. Locally both must be on `PATH` (e.g. `brew install yt-dlp gallery-dl` or `uv tool install`).
- `bun install` runs with `--ignore-scripts`: the `gifsicle` npm package has no linux/arm64 binary and its postinstall tries to compile from source. Only sharp's install script is run (downloads libvips), and the npm gifsicle path is symlinked to `/usr/bin/gifsicle`. A new dependency that needs an install script must be run explicitly in the Dockerfile.
- gifsicle versions differ (verified 2026-11): the npm package's prebuilt binaries (macOS, linux x64, Windows) are **1.93** and never updated; Debian's apt package in the image is **1.96**. So local dev runs 1.93 and the container 1.96 on every architecture. The flags used are the same in both, but output sizes can differ slightly. Using the system binary everywhere (brew/apt) would remove the mismatch and the Dockerfile workaround.
- Manager, API and all shards run in one container.

## Agent pitfalls (core)

- New command/button = new file in the right directory with `export default`. No manual registration, but slash commands must be deployed (`deploy:dev`).
- Always work with an emote through `ProcessingEmoteService`, never directly through files.
- `emote.animated` is determined from the file in `store()`. Don't trust flags from sources.
- Change optimization only in `src/lib/buffer/` and verify on real GIFs (size, dimensions, frame count, total delay).
- API code runs in the manager process, bot code in the shards. See the `@/bot` warning above.
- A running `dev` picks up every file change immediately, including uncommitted edits, and executes it against the real bot token and the local DB. Don't keep it running while code is being changed, and check for orphaned shards afterwards (`pgrep -fl src/bot.ts`).
- Don't start the bot (or load modules that import `@/bot`) in tests unless asked; the token in `.env` may be the production one.
- Verify assumptions about Discord and the emote APIs against their docs or live responses before changing code.
